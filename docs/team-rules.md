# 팀 작업 규칙

사람과 AI 에이전트(Claude Code, Codex 등)가 모두 지키는 규칙이다. 작업 전에 끝까지 읽는다.

- 할 일: 팀원마다 받은 작업 문서(리포지토리 밖에 있고 각자 가지고 있음)대로 진행한다.
- 고칠 수 있는 파일에 제한은 없다. 작업에 필요하면 어느 파일이든 고친다. 다만 3~5절의 게임 내용 규칙은 지킨다.

> **작업 전에 무조건 `git pull`한다.** 예외 없음. Unity를 닫고 작업 브랜치에서 `git pull`한 뒤에 Unity를 연다. push하기 직전에도 한 번 더 `git pull`한다. 명령은 8.2절에 있다.
> 왜: 여러 사람이 한 브랜치에 push한다. pull하지 않고 작업하면 다른 사람이 고친 것 위에 옛날 파일을 덮어쓰거나, 이미 바뀐 내용을 모르고 작업하게 된다.

팀에 전할 말은 [notices.md](notices.md)(공지)에 올린다. 에이전트가 pull한 뒤 새 공지를 알려 준다(0절).

## 0. 에이전트 설정 (각자 한 번)

사람은 이 절을 읽지 않아도 된다. 리포지토리를 받은 뒤 쓰는 에이전트(Claude Code 또는 Codex)에게 아래 문장을 그대로 보내면 된다.

```
docs/team-rules.md 0절대로 에이전트 설정해줘
```

### 에이전트가 할 일

설정 파일은 `.gitignore`에 들어 있어 커밋되지 않는다. 사람이 쓰는 에이전트가 무엇이든 아래 두 파일을 모두 리포지토리 최상위에 만든다.

1. `CLAUDE.md` (Claude Code가 읽음)
   - 파일이 없으면 아래 한 줄로 만든다.
   - 파일이 있으면 내용을 지우지 말고, 이 줄이 없을 때만 맨 위에 추가한다.

   ```
   @docs/team-rules.md
   ```

2. `AGENTS.md` (Codex가 읽음)
   - 파일이 없으면 아래 내용으로 만든다.
   - 파일이 있으면 내용을 지우지 말고, 이 문장이 없을 때만 맨 위에 추가한다.

   ```
   작업 전에 docs/team-rules.md를 끝까지 읽고 그 규칙을 지킨다.
   ```

3. `git check-ignore CLAUDE.md AGENTS.md`를 실행해 두 파일이 모두 무시되는지 확인한다. 무시되지 않으면 커밋하지 말고 사람에게 알린다.
4. 두 파일은 `git add`, 커밋, push하지 않는다.
5. 끝나면 사람에게 알린다: "설정을 마쳤어요. 에이전트를 껐다가 다시 켜면(새 세션) 규칙이 적용돼요."

### 에이전트가 작업을 시작할 때 (매번)

사람이 작업을 시키면 파일을 읽거나 고치기 전에 아래를 먼저 한다.

1. 사람에게 묻는다: "Unity를 닫았나요?" 닫았다고 답할 때까지 다음으로 가지 않는다.
2. `git branch --show-current`로 지금 브랜치가 작업 브랜치(8.1절)인지 확인한다. 아니면 사람에게 8.2절 명령으로 바꾸라고 알린다.
3. `git pull`을 실행한다.
4. pull이 실패하면(충돌, 커밋하지 않은 변경 때문에 거절 등) 충돌이면 `git merge --abort`로 되돌리고, 사람에게 오류 내용을 그대로 알린다.
5. pull이 성공하면 [notices.md](notices.md)(공지)를 읽는다.
   - `CLAUDE.md`·`AGENTS.md`의 `마지막으로 본 공지: N` 줄에서 N을 읽는다. 줄이 없으면 0으로 본다.
   - 번호가 N보다 큰 공지를 사람에게 빠짐없이 그대로 보여 준다. 요약하거나 건너뛰지 않는다.
   - 보여 준 뒤 두 파일의 `마지막으로 본 공지:` 줄을 공지 문서에 있는 가장 큰 번호로 고친다. 줄이 없으면 맨 아래에 추가한다. 두 파일은 커밋하지 않는다.
6. 그다음 사람에게 "최신으로 받았어요. 이제 Unity를 열어도 돼요."라고 알리고 작업을 시작한다.

push할 때도 8.2절 순서(`git pull` 뒤 `git push`)를 지킨다.

## 1. 프로젝트

- 제1형·제2형 당뇨병 초등학생 아동이 유형별 대처와 혈당 관리 습관을 익히는 교육용 기능성 게임(serious game)이다. 3D 러너(3레인, 좌우 이동, 점프, 슬라이드)다.
- Android 단독 앱이다. 서버가 없고 인터넷을 쓰지 않는다.
- 전체 방향은 [type-tracks.md](type-tracks.md)에 있다.

## 2. 코드 규칙

- 입력은 Input System(`UnityEngine.InputSystem`)으로만 받는다. 구 입력 API(`UnityEngine.Input`)를 쓰지 않는다. 왜: 이 프로젝트 설정에서는 구 API가 실행 중에 오류를 낸다.
- 네트워크 API를 쓰지 않는다. 왜: 아동 데이터가 기기 밖으로 나가지 않는 것이 전제다.
- **확인**: Unity Console 창에 빨간 오류가 없어야 한다. 동작을 확인한 뒤 작업 브랜치에 push한다.

## 3. 게임 내용에서 절대 하지 않을 것

그림, 애니메이션, 소리, 문구 모두에 적용한다.

- **치료·진단 주장 금지**: 의료기기나 디지털 치료제가 아니다. "치료된다", "낫는다", "진단" 같은 표현을 쓰지 않는다.
- **"죽음", "생존" 표현 금지**: 탈락은 어른이 도와주러 오는 장면이다. 쓰러짐, 해골, 묘비 같은 연출도 쓰지 않는다.
- **체형 변화 금지**: 혈당이 높을 때 캐릭터가 부풀거나 뚱뚱해지는 연출을 만들지 않는다. 혈당 상태는 표정(지친 얼굴), 걸음(느려짐), 자세(처짐)로만 나타낸다. 왜: 의학적으로 틀렸고, 체중 놀림을 가르치게 된다.
- **"나쁜 음식" 금지**: 햄버거, 치킨, 주스 등 어떤 음식도 나쁘거나 무섭게 그리지 않는다(찡그린 얼굴, 해골 표시, 빨간 X 등). 왜: 음식 죄책감과 섭식 문제로 이어질 수 있다.
- **"아파한다" 대신 "지쳐 보인다"**: 고통스러워하는 표정·소리를 쓰지 않는다.
- **가짜 신호 금지**: 혈당이 정상일 때 증상처럼 보이는 연출을 만들지 않는다.

## 4. 의학 정보

- 의학 정보, 증상, 음식이 혈당에 주는 영향을 지어내지 않는다. 에이전트가 아는 지식으로 채우는 것도 지어낸 것이다.
- 출처는 세 가지만 쓴다: 대한당뇨병학회 진료지침, ISPAD Clinical Practice Consensus Guidelines, ADA Standards of Care.
- 판본은 [medical-sources.md](medical-sources.md)에 정해진 것만 쓴다. 항목마다 어느 장을 보면 되는지도 거기 있다.
- 출처를 적을 때는 자료명, 판본(연도), 장 또는 페이지를 적는다. 확인하지 못한 칸은 비워 둔다.
- 기사·요약 같은 2차 출처로 권고 내용을 인용하지 않는다. 원문을 연다.

## 5. 수치

- 혈당 수치, 시간, 점수 가중치를 지어내지 않는다. 값의 근거는 [glucose-evidence.md](glucose-evidence.md), [game-values.md](game-values.md)에 있다.
- 그림이나 문구에 혈당 숫자(예: "70 이하면 위험")를 넣지 않는다.

## 6. 에셋

- **유료 에셋 금지**: 공개 리포지토리다. 유료 에셋과 라이선스가 불분명한 에셋은 커밋하지 않는다. API 키, 비밀번호도 커밋하지 않는다.
- **라이선스 기록**: 외부 에셋을 쓰면 `Assets/_Project/Art/LICENSES.md`에 한 줄씩 적는다. 형식: `| 파일 또는 폴더 | 출처 URL | 만든 사람 | 라이선스 |`. 직접 만든 것은 출처에 "직접 제작"이라고 적는다.
- 큰 파일(그림, 모델 등)은 Git LFS로 올라간다(설정되어 있음). LFS가 아닌 파일이 10MB를 넘으면 커밋 훅이 막는다.
- 모바일 게임이다. 모델과 텍스처는 가볍게 만든다(로우폴리 권장).

## 7. Unity 작업

- Unity 에디터는 `6000.3.26f1`만 쓴다(패치 번호까지 같게). 다른 버전으로 열면 파일이 바뀐다.
- 파일 이동, 이름 변경, 삭제는 Unity 에디터 Project 창에서 한다. 탐색기·Finder·명령어로 하지 않는다. 왜: 짝이 되는 `.meta` 파일이 깨지면 커밋 훅이 막고, 다른 곳에서 쓰던 연결이 끊긴다.
- 새 파일을 커밋할 때 `.meta` 파일도 함께 커밋한다.
- 같은 씬이나 같은 프리팹을 두 사람이 동시에 고치지 않는다. 고치기 전에 팀에 알린다. 왜: 씬·프리팹 충돌은 손으로 풀기 어렵다.
- 브랜치를 바꿀 때는 Unity를 먼저 닫는다.

## 8. Git

- `dev`, `main`에 직접 push할 수 없다.

### 8.1 브랜치 흐름

```
dev
 └─ <작업 브랜치>   ← 모두 이 브랜치를 받아 그 위에서 작업하고 push
 ← 할 일이 모두 끝나면 dev로 PR해 머지
```

- 작업 브랜치는 하나다. 지금은 `feat/section2-frame`이다. 아래 명령의 `<작업 브랜치>`를 그 이름으로 바꿔 쓴다.
- 여러 사람이 한 브랜치에 push하므로, 작업을 시작하기 전과 push하기 전에 **무조건** `git pull`한다. 어제 pull했어도, 5분 전에 pull했어도 다시 한다.
- 작업 브랜치를 `dev`에 머지할 때는 README 4절대로 팀원 1명 승인을 받는다.

### 8.2 명령어

Unity를 닫은 뒤 실행한다.

처음 작업 브랜치를 받을 때:

```bash
git fetch
git switch <작업 브랜치>
```

작업을 시작할 때마다(무조건, Unity를 열기 전에):

```bash
git switch <작업 브랜치>
git pull
```

작업을 올릴 때:

```bash
git add <고친 파일과 .meta 파일>
git commit -m "<type>: <영어 문장>"
git pull
git push
```

- `git pull`에서 충돌(conflict)이 나면 `git merge --abort`로 되돌린 뒤 팀에 알린다.
- `git push`가 거절되면(다른 사람이 먼저 push함) `git pull` 뒤 다시 `git push`한다.

### 8.3 커밋과 PR

- 커밋 메시지는 한 줄만 쓴다. 형식: `<type>: <대문자로 시작하는 영어 문장>`, 끝에 마침표 없음. 본문, `Co-Authored-By` 같은 꼬리말을 붙이지 않는다.
  - type: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
  - 예: `feat: Add runner character model`, `chore: Add jump sound`
- 작업 브랜치를 `dev`로 올리는 PR: 제목 `<type>: Merge <작업 브랜치> into dev`, 본문 `- 내용` 한 줄씩, 짧은 한국어 명사형·음슴체(예: `- 주인공 달리기 애니메이션 추가`).
- 작게, 자주 커밋하고 push한다. 에셋 묶음 하나에 커밋 하나.

## 9. 막히면

- 확실하지 않은 Unity 사용법이나 패키지 정보는 추측하지 말고, 공식 문서로 확인했는지 밝힌다.
